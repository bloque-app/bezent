# I-14

## What it is

Correlation that cannot be computed: an identifier composed by the runtime was unknown in advance, so operations were
matched to events by position (`notes/BRIDGE-REQUIREMENTS.md` §5, "Bloque's internal incident records").

What bezent does: the on-chain reference is written by the transaction of each movement, atomically with the value, and legs
are matched to transfers by it, never by position in a batch or by an amount (`REQ-ID-2`, `REQ-OT-2`). A redemption's reference
is the redeemer together with the reference it chose, so two redeemers with one reference are each paid by their own payout.
A payout carries a reference derived per withdrawal; the leg carries reference, token, sender and recipient. A leg observed
twice under one reference is ambiguous and held as unknown, never a pick; it reaches review past its deadline.
Grouping several transfers in one transaction is allowed only if each keeps its own reference and proof (`REQ-EO-5`).

## Pages

None. An ambiguous leg appears as an unknown leg, then as a review.

## Confirm

```sql
SELECT metric, asset, network, direction, value FROM ops_observables() WHERE metric IN ('unknown_legs', 'reviews_open');
SELECT transfer_id, kind, asset, condition, state_before_review, entered_at FROM reviews ORDER BY entered_at;
```

The legs under a reference are in `observations`, which the operator login cannot read; take them from the requester-facing
status by bridge reference or coordinate (`REQ-ST-2`), or from public chain data.

## Do

- For an ambiguous leg, hold: do not pick one. Read both coordinates from public chain data and resolve the review by the
  coordinate that settles it (`manual_actions`; `manual_approvals` by another login where value moves, `REQ-RV-2`).
  The core verifies the coordinate against what the endpoints recorded at final blocks before it runs the edge.
- If a leg carries the reference but not the shape expected (token, sender, recipient), it is not the transfer's delivery; the
  core sends the transfer to review. Do not match it by amount or time.

## Never

- No matching by amount, time or position (`REQ-OT-2`, `REQ-ID-2`); a reference alone is not authority to change a transfer (`REQ-ID-4`).
- No UPDATE or INSERT on transfers, observations or references (`INV-2`, `REQ-GV-5`).
- No refund or failure on a timer or an unknown (`REQ-RF-1`, `REQ-RV-1`).

## Exercise

Drill on a test network: make two redeemers use one reference, and separately make a payout leg appear twice; confirm each
redeemer is paid by its own payout and the doubled leg is held as unknown. Record who, when and what was found here.
