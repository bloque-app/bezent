# I-7

## What it is

"Could not look" read as "did not happen": a dropped watcher connection quarantined a transfer that had succeeded, and
undecodable events were reported as failed, which triggers a refund (`notes/BRIDGE-REQUIREMENTS.md` §5, "Bloque's
internal incident records").

What bezent does: silence, elapsed time, a node's "not found", a connection error, an event it cannot decode and a dropped
transaction are each unknown, never proof (`REQ-NX-3`). Providers that disagree prove nothing. A reading that cannot be made
is recorded as unknown with its reason, so a reserve evaluation that cannot read is `incomplete`, never `holds`. A delivery
anomaly (what an endpoint reads contradicts itself) sends the transfer to review at once and moves nothing; nothing is
refunded because of it (F-003 NOTES, "Delivery anomalies"). Since amendment 0028 an evaluation that cannot read holds the
asset's routes at once (new work waits, work in flight continues), and the core lifts the hold itself at the first
evaluation that holds. Residual: transfers held unknown, or an evaluation that stays incomplete.

## Pages

`reserve-blind` once the asset has been held blind beyond its bound; `reserve-check-incomplete` is recorded, no longer
paged; `reserve-check-stalled` only when even the failure could not be recorded (`../pages/reserve.md`);
`key-compromise` where a consumer is not one bezent recorded (`../pages/key-compromise.md`).

## Confirm

```sql
SELECT metric, asset, network, value FROM ops_observables()
 WHERE metric IN ('reserve_equation_outcome', 'reserve_equation_age_seconds', 'unknown_legs', 'open_gaps', 'reviews_open');
SELECT asset, outcome, reason, evaluated_at FROM reserve_evaluations ORDER BY id DESC LIMIT 10;
SELECT network, kind, subject, amount, unknown_reason, recorded_at FROM reserve_readings WHERE amount IS NULL ORDER BY id DESC LIMIT 10;
```

Outcome 2 in `reserve_equation_outcome` is "could not be made" or "cannot see", not "diverges". `SELECT id, asset, kind
FROM pauses WHERE kind = 'hold'` shows the hold.

## Do

- Restore the read (provider, connection) from the deployment's own notes; the next cycle re-reads. Nothing is decided meanwhile.
- While the evaluation is incomplete the core holds the asset itself, and lifts the hold itself once an evaluation holds;
  do not lift it by hand (`operator_request_unpause` refuses a hold). A pause left from before amendment 0028 (cause
  `REQ-IC-2` naming an evaluation) is lifted only with a second person: `operator_request_unpause`, then
  `operator_approve_unpause` by a different login.
- A transfer in review from an anomaly ends only by a final coordinate (`manual_actions`, a second approver where value
  moves), as in `I-1.md`.

## Never

- No "unknown" read as "failed", "not executed" or "did not happen"; no refund on it (`REQ-NX-3`, `REQ-RF-1`).
- No decision on a non-final read (`INV-16`).
- No UPDATE or INSERT on transfers, readings or evaluations (`REQ-GV-5`).
